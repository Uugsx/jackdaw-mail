# Целостность локальной базы писем

Инцидент 2026-11-09 (PR #175–#178): номер строки `email.id` переиспользовался,
объект письма в памяти держал номер удалённой строки, а исходник MIME в
`mail-backup.db` искался по номеру — письма Exchange показывали чужой текст и
вложения. Чтобы такое ловилось до выпуска и лечилось у пользователя, есть три
проверки. Общий код — `app/logic/Mail/SQL/SQLIntegrity.ts`.

## Инварианты

| Инвариант | Что значит | Вредно |
|---|---|---|
| `foreignSource` | колонка `emailMIME.messageID` ≠ Message-ID строки письма с тем же номером | да |
| `foreignSourceHeader` | заголовок Message-ID исходника ≠ Message-ID строки письма | да |
| `sourceColumnMismatch` | колонка `messageID` исходника ≠ его заголовку (старый код пересохранял чужой исходник под своим Message-ID) | да |
| `orphanAttachment`, `orphanTag`, `orphanRecipient` | строка дочерней таблицы без строки `email` | да |
| `duplicateRow` | одно письмо (папка + pID, или папка + Message-ID без pID) сохранено несколько раз | да |
| `idCounter` | нет счётчика `emailIDCounter`/триггера или он меньше `MAX(email.id)` — номера удалённых писем снова выдаются | да |
| `orphanSource` | исходник без строки письма | нет, пока номера не переиспользуются |

Письма, которые сравнить нечем (нет Message-ID у письма или у исходника), не
считаются нарушением и не лечатся.

## 1. Тест в CI

`app/test/logic/Mail/SQL/integrityFuzz.test.ts` входит в `npm run test:regression`.
30 случайных последовательностей по 45 шагов: приход писем (по одному и
пачкой), повторная синхронизация, удаление (в том числе другим путём, пока
объекты держат старый `dbID`, и удаление письма с наибольшим номером), перенос
на сервере и локально, чистка дублей миграцией, флажки и категории объектами с
устаревшим `dbID`, сохранение исходника MIME, открытие письма, перечитывание из
базы. После каждого шага проверяются инварианты выше и, по эталону, что текст,
pID, вложения, категории и отправитель каждой строки — её письма, а номера
удалённых строк не выдаются снова.

Проверено: на коде до #176–#178 тест падает (счётчик номеров; исходник письма
m1 под строкой m2 на 19-м шаге; чужая категория через устаревший `dbID` на
25-м шаге при выключенных проверках исходников), на main проходит.

При изменении сохранения, удаления, синхронизации или чистки писем — добавить
операцию в тест, если её там нет.

## 2. Проверка копии реальной базы перед выпуском

Перед выпуском правок базы, синхронизации или удаления писем — из каталога `app`:

```bash
npx tsx scripts/db-integrity-check.ts --snapshot /путь/к/пустой/папке
```

`--snapshot` снимает копию `mail.db` и `backup/mail-backup.db` из профиля
(`~/Library/Application Support/Jackdaw`, другой — `--profile`) через
`VACUUM INTO`: оригинал открывается только на чтение. Уже снятую копию:

```bash
npx tsx scripts/db-integrity-check.ts /путь/к/копии
```

Скрипт отказывается открывать сам профиль и открывает копию только на чтение.
Печатает число нарушений каждого инварианта и примеры; `--json` — отчёт в JSON,
`--no-headers` — без чтения заголовков исходников (быстрее). Код выхода 1 —
есть вредные нарушения. Сравнивать с прогоном до правки: новые нарушения —
регрессия.

Копия базы владельца, 2026-11-09 (0.10.320): 74 528 писем, 89 631 исходник,
13,5 с. Чужих исходников — 43 по колонке, 44 по заголовку (в том числе один
пересохранённый под своим Message-ID), висячих исходников — 48 569, дублей
строк — 79, счётчик в порядке.

## 3. Проверка при запуске приложения

`app/logic/Mail/SQL/repairOnStartup.ts`, из `loginOnStartup()` главного окна
(не в демо-режиме), через 10 с после старта, в фоне. Находит письма с чужим
исходником, удаляет этот исходник, сохранённый текст и вложения и снимает
`downloadComplete` — письмо загрузится с сервера заново. Пишет в консоль
«Проверка базы писем: исправлено писем с чужим исходником — N».

Колонка Message-ID сверяется у всех исходников каждый запуск (на базе
владельца — доли секунды, по покрывающим индексам). Заголовки читаются только у
исходников с `emailMIME.id` больше проверенного в прошлый раз
(`localStorage`, ключ `mail.integrity.sourceHeadersCheckedUpTo`), пачками по
500 с паузой: `INSERT OR REPLACE` выдаёт новому или пересохранённому исходнику
новый `id`. Строку Message-ID вырезает SQLite из первых 16 КБ исходника —
в окно приходит около 1 КБ на исходник, а не гигабайты.
